# mStock production connection

Use a Type A API key and the broker account that belongs to your dashboard workspace.

1. Sign in with Google. The same verified Google UID always opens its existing server workspace, including its broker link and current day-session, on every device. A valid broker connection opens directly without setup.
2. For a first Type A Authenticator connection, enter the API key and current six-digit Authenticator code. This calls the documented `/session/verifytotp` endpoint with only `api_key` and `totp`. The key is encrypted on the server after broker verification. When that saved TOTP session expires, the returning-user form needs only the current six-digit code; it reuses the private server key and checks that mStock returns the same broker account before saving the new token. It never fetches the key into the browser. SMS OTP and full client-code/password login remain available as a fallback, including for a broker response that requires the full flow. If mStock shows Disable TOTP, Authenticator is enabled and SMS OTP is not sent.
3. Wait for the account check to confirm the session. A temporary read failure retries automatically using the encrypted saved token; do not generate another code just because the market stream reconnects.
4. Use the read-only account checks to verify funds, permissions and data access. Order-book access is not proof of a live fill.

When TOTP is enabled, mStock does not send an SMS OTP for the trading API login. Use the current authenticator code. The app does not remove or disable broker two-factor verification.

Access tokens expire within 12 hours or at midnight IST, whichever comes first. Expired or rejected tokens require a fresh login; passwords and OTPs are not stored for unattended renewal. Temporary verification failures use bounded retries (5–60 seconds); invalid credentials/API keys do not loop indefinitely.

An expired token is distinct from a removed account link. The saved account remains visible in Profile and the broker dialog while verification is due. Authentication renewal preserves the original session ID, reference prices, rules and ledger and does not submit any trading order or implicitly start a new trading day. Requests to renew an already valid saved connection or replace a connected running strategy are rejected. TOTP flows are rate-limited with ordinary login, expire after ten minutes, allow at most five verification attempts, and cannot switch to SMS OTP within the same flow. After a flow expiry or engine restart, use Restart verification; codes are only submitted on an explicit user action.

Google sign-in persistence follows [Firebase's documented local persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence). Broker token validity remains governed by [mStock's published limits](https://tradingapi.mstock.com/docs/v1/Introduction/). A returned `refresh_token` field is not treated as permission to use an undocumented silent-renewal endpoint. The partner redirect flow is a separate partner integration and is not substituted for the retail Type A flow.

Market streaming is separate from broker authentication. A stream reconnect does not log out the broker. Quiet subscribed contracts do not tear down a stream that is delivering other instruments. Outside normal weekday market hours, absent ticks alone do not force reconnects. Missing or stale prices never become executable prices just because the socket is open.

Execution IP setup is under **API key & execution IP setup**. Each Google workspace requires its own reserved outbound route with a distinct observed public IPv4. This prevents account collisions such as *"IP already used"*. The operator supplies existing routes through `N009_WORKSPACE_PROXIES` / `N009_WORKSPACE_INTERFACES`; the allocator tests them and reserves one before broker login. An existing dedicated HTTP/HTTPS route can also be configured through the workspace setup panel. Both REST calls (`MStock`) and market WebSocket connections (`MarketFeed`) use that route.

Concurrent sign-ins share one allocator. Reservations remain attached to the same workspace across disconnects, devices and restarts. All persisted reservations load before new allocations, and different route URLs that exit through the same public IPv4 cannot be assigned to separate workspaces. A pool with insufficient working IPs leaves additional Google workspaces **Not assigned** and blocks broker login and new Live starts. It does not offer the shared host IP for registration. Adding available routes allows unassigned workspaces to retry on their next request; failed probes are cached for up to 30 seconds. No paid dependency or address provisioning is added.

`N009_WORKSPACE_INTERFACES` contains local interface addresses, not arbitrary public addresses. The host network must already route each interface to a distinct public IPv4. Multiple interfaces sharing one NAT address are one public IP. IP observation confirms current routing only; the operator must ensure the allocation stays static. A detected change from a route's saved public IP blocks reconnection and new Live starts until routing is corrected. Existing broker links are never moved to a new route automatically: stop and flatten, disconnect, then configure the new route and reconnect. Keep routes private; proxy credentials stay on the execution server and are omitted from network reports.

Register the assigned outbound execution IPv4 as the **Primary IP** on `trade.mstock.com` (never the browser/device IP or Vercel website domain). A saved IP reference in this app does not change broker settings. The official Type A flow (API key + Authenticator TOTP, with client-code/password/SMS OTP fallback) uses the workspace's route. Account Diagnostics tests read-only broker access; it does not retrieve or certify the broker's registered IP list. A fresh verified broker login can move a connection from a stopped, flat workspace with no pending order; the previous workspace keeps its history and loses its broker credentials, while active sessions cannot be moved.

The public Type A API reference documents authentication and server-side API usage; it does not document an API that provisions public IPs or edits the broker whitelist. mStock's [connectivity guidance](https://www.mstock.com/articles/limitations-of-trading-api-platforms) describes static-IP whitelisting. Its [partner onboarding flow](https://tradingapi.mstock.com/docs/v1/Partners-Onboarding/login-flow/) is a separate integration requiring platform credentials issued by mStock; retail keys cannot be substituted for those credentials. Do not infer an exact retail account-sharing policy from the partner flow.

Provider comparison checked on 12 November 2026: [Stocks Developer's documentation](https://stocksdeveloper.in/documentation/static-ip-setup/) describes account-level IP assignment and bringing an existing dedicated proxy, followed by broker whitelisting. That is the allocation pattern used here with existing infrastructure. [AlgoRooms](https://algorooms.com/) describes broker-connected execution, but its public pages did not establish its per-account IP allocation method or mStock partner status. No undocumented AlgoRooms mechanism is assumed.

### Release and reuse an assigned IP

In **IP & Route**, use **Release assigned IP** after stopping and flattening the strategy and disconnecting mStock. This releases only the signed-in workspace's route; broker credentials, account ownership and history are not transferred to another user. The server rejects release while a broker link, active/blocked session, position, pending order or broker request remains. Abandoned login codes are invalidated when the route changes.

A released account stays unassigned across refreshes, background polling, devices and engine restarts. **Recheck** explicitly requests an available route again. In another account, **Recheck** claims an available operator-pool route; if none is free, the account stays unassigned. Concurrent requests cannot claim the same route. Release does not edit mStock's official IP registration: remove the old broker registration before another client registers that address.

Local preview uses the hosted account engine by default (`scripts/dev.mjs` and `vite.config.ts`). Incognito and a different Google account create separate authenticated workspaces; neither changes the engine’s public IP. Every Google workspace requires its own assigned route even when execution-location metadata is local or unspecified. The preview also handles older engine responses that only report a shared-host conflict by showing **Not assigned** and withholding the host IP from copying.
